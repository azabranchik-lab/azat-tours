# azattours.com: полный анализ (архитектура, скорость, SEO, оптимизация)

Дата: 2026-10-25. Замеры с прода. Исходники: `seo-audit/baseline/`, `seo-audit/lighthouse/*.report.html`
(открываются в браузере), `seo-audit/phase-0-report.md`.

## 0. Резюме в десяти пунктах

1. **Техническое SEO в порядке.** Lighthouse SEO 100 на всех типах страниц, 92 URL в индексе без единой ошибки
   (title, description, canonical, H1, JSON-LD, 301 со старых адресов). Задача не «починить», а «выжать больше».
2. **Скорость на телефоне средняя: 65–86 баллов.** Каталог 65 (LCP 6,2 с), тур 73 (LCP 5,1 с), главная 86, статья 85.
   Google считает хорошим LCP до 2,5 с. Это главный технический резерв.
3. **Причины медленного LCP все дешёвые в исправлении:** заголовок и кнопки hero скрыты `opacity:0` до события
   `window.load`; три семейства Google Fonts (161 КБ) с внешнего домена блокируют текст; Google Analytics 177 КБ
   (в 7 раз больше всего нашего JS) грузится сразу; у 1406 картинок нет `width/height`; у карточек нет `srcset`
   (телефон качает фото 1280 px для карточки 360 px); CSS и JS отдаются с `no-cache`.
4. **Сервер отдаёт HTTP/1.1.** nginx без `http2`: 27–37 запросов на страницу идут в 6 соединений по очереди.
   Включение HTTP/2 это одна строка в конфиге nginx (нужен доступ к серверу).
5. **Сервер в Сингапуре, аудитория в Европе и США.** Первый байт 260–510 мс, из Европы хуже. Лечится CDN
   (Cloudflare, бесплатный тариф): TLS на ближайшем узле, HTTP/3, brotli, кэш статики. Для корейской версии
   Сингапур как раз хорош.
6. **Контент сайта существует только на сервере.** `content/*.json` и фото не в git и не копируются никуда.
   Падение диска VPS = потеря 80 туров с текстами и заявок. Нужен ночной бэкап, это важнее любого SEO.
7. **Внутренняя перелинковка слабая.** 37 из 77 туров не получают ни одной ссылки кроме каталога; ни один тур не
   ссылается на статьи блога; главная ведёт на 6 туров, а 4 карточки «must-see» на каталог целиком.
8. **Каннибализация запросов.** 19 серий туров отличаются только длительностью (например 6 вариантов
   «ultimate road trip» 7–12 дней, 5 «best of» 8–12 дней). Для Google это 5–6 почти одинаковых страниц под один
   запрос, и ни одна не сильная. Решается хабами и канониклами (фаза 3), не удалением.
9. **Названия туров построены от географии, а люди ищут «Kyrgyzstan horse trek 3 days».** Title содержат
   «Kyrgyzstan» (сервер дописывает), но H1 и первые слова нет. Переименование title/H1 без смены slug, фаза 3.
10. **Доверие (E-E-A-T):** отзывов нет вообще (блок скрыт), нет ссылок на TripAdvisor/Google, у половины
    многодневных туров нет цены. Это сильнее влияет на конверсию и ранжирование, чем любая техника. Фаза 2.

## 1. Архитектура

### Как устроено
```
Браузер ──HTTPS──> nginx 1.24 (TLS, HTTP/1.1) ──> Node http (server.js, pm2 "azat-tours", 1 процесс)
                                                    ├─ lib/pages.js: рендер HTML из content/*.json + шаблонов public/*.html,
                                                    │   кэш в памяти по mtime, gzip-кэш по ETag
                                                    ├─ статика public/ (AVIF/WebP по Accept, картинки кэш 7 дней)
                                                    ├─ /api/lead, /api/chat (JSON-файлы, уведомления в Telegram)
                                                    └─ bot.js (grammY, админка владельца) в том же процессе (start.js)
Деплой: push в main → GitHub Actions по SSH → git reset --hard → npm ci → migrate.js → regenerate-all.js → pm2 reload
Контент: content/*.json на сервере (не в git), правится ботом; public/*-data.js генерируются из него
```

### Что хорошо
- Серверный рендер без фреймворка: весь контент в HTML, ~9 КБ gzip на страницу тура, отдача из кэша за <3 мс.
- Один источник данных для HTML, sitemap, llms.txt, .md-версий и JSON-LD: ничего не расходится.
- Правка в боте видна на сайте через секунду без деплоя. Миграции контента идемпотентны и логируются.
- Старые адреса покрыты 301 в коде, nginx не нужен. `check-site.js` уже ловит регрессии.
- Форма заявки идёт на `/api/lead` с honeypot и rate limit; в Telegram прилетает карточка с кнопками.

### Риски и долги
| Риск | Почему важно | Что делать |
|---|---|---|
| Нет бэкапа `content/` и `public/images/` | Единственная копия живого контента на одном VPS | Ночной cron: `tar` в S3/Backblaze или `git push` снимка в приватный репозиторий; хранить 30 дней |
| Сайт и бот в одном процессе | Падение бота (ошибка Telegram API) перезапускает сайт | Разнести на два pm2-процесса (`server.js` и `bot.js`), уже поддерживается кодом |
| HTTP/1.1, нет brotli, нет CDN | Лишние 0,5–1,5 с на телефоне, нагрузка на VPS | `http2 on;` + `brotli` в nginx; затем Cloudflare перед сервером |
| `Cache-Control: no-cache` на CSS/JS | Каждый переход валидирует 6–9 файлов, по HTTP/1.1 это очередь | Версия в имени (`styles.<hash>.css`) + `max-age=31536000, immutable`; HTML оставить `no-cache` |
| В `public/` лежат `*.bak` и неиспользуемые файлы | Мусор в репозитории, риск случайно отдать | Убрать из репо (`*.bak` уже в `.gitignore`, но файлы есть) |
| В `script.js` остался ключ Web3Forms и «DEMO mode» | Мёртвый код, вводит в заблуждение; ключ публичный | Удалить ветку Web3Forms, оставить только `/api/lead` |
| Нет мониторинга доступности | Узнаём о падении от клиентов | Бесплатный UptimeRobot/BetterStack на `/` и `/api/chat?sid=ping` |
| GA4 без согласия на куки | Для посетителей из ЕС формально нужно согласие | Либо баннер (вариант C из плана), либо GA в режиме без куки до согласия |
| Партнёрский бот в том же репозитории и деплое | Ошибка в `partners/` ломает деплой сайта | Отдельный workflow или хотя бы `continue-on-error` для шага партнёров |

### Почему LCP 5–6 с и как это чинится
1. **Hero скрыт до `load`.** `.reveal{opacity:0}` снимается для hero только в `window.addEventListener('load')`,
   то есть после всех картинок, шрифтов и gtag. Заголовок H1 (кандидат в LCP) появляется последним.
   Исправление: показывать hero сразу (класс `in` в разметке или инлайн-скрипт в `<head>`), анимировать остальное.
2. **Шрифты блокируют текст.** `display=swap` есть, но CSS шрифтов идёт с другого домена, затем три файла.
   Исправление: самохостинг двух семейств с подмножеством latin, `preload` основного, Figtree заменить системным
   стеком или оставить только его как единственный текстовый. Решение по шрифтам за владельцем (дизайн).
3. **gtag.js 177 КБ сразу.** Исправление: грузить после `load` или по первому взаимодействию/через 3 с idle.
   Статистика не пострадает, просмотр засчитается.
4. **Картинки без размеров и `srcset`.** CLS на каталоге 0,134 (`.wrap`: панель фильтров вставляется JS после
   загрузки и сдвигает список), на туре 0,063 (`.hl-grid`). Исправление: `width/height` из метаданных файла
   (sharp уже есть), `srcset` 480/800/1280 для карточек и галереи, панель фильтров рендерить сервером или
   резервировать высоту.
5. **HTTP/1.1 и `no-cache`.** 28 запросов в 6 параллельных соединений, CSS/JS каждый раз валидируются.
   Исправление: HTTP/2 в nginx, версионированные имена и долгий кэш.
6. **Сервер далеко.** 260–510 мс первого байта. Исправление: Cloudflare (бесплатно) или перенос VPS во Франкфурт.
   Каталог отдаёт 510 мс, потому что 110 КБ HTML сжимается при первом запросе после рестарта и дальше из кэша.

Ожидаемый эффект пунктов 1–4 (без доступа к серверу): LCP 2,0–2,8 с, Perf 85–95 на всех типах.
Пункты 5–6 добавляют ещё 0,3–0,8 с всем посетителям, особенно из Европы и США.

### Мелочи
- Каталог: 79 карточек в HTML (110 КБ), это нормально для SEO, но на телефоне 79 `<img loading=lazy>`;
  можно отдавать первые 12 с `fetchpriority`, остальные как есть. Карточка берёт фото 1280 px.
- Hero главной: `preload` с `imagesrcset` есть, первая картинка 34 КБ AVIF, хорошо.
- `chat.js` (6 КБ) и его CSS (6,5 КБ) на каждой странице, виджет опрашивает `/api/chat` каждые 20 с только после
  первого сообщения. Приемлемо, можно грузить по idle.
- Inline SVG иконок до 28 штук на страницу, это дёшево.

## 3. SEO

### 3.1 Техническое (состояние: хорошо)
- 92 URL в sitemap, все 200, canonical = URL, по одному H1, без noindex; дублей title/description нет.
- Sitemap генерируется из данных; лишние `changefreq/priority`; `lastmod` служебных страниц от mtime файла
  (после деплоя у всех одна дата). Индекса sitemap пока не нужно (меньше 200 URL), понадобится с `/ko/`.
- 301: 257 старых адресов за один хоп на нужную страницу. Неизвестный slug отдаёт 404 (рекомендую оставить).
- robots.txt открыт, `llms.txt`, `llms-full.txt` и `.md`-версии есть (редкость, плюс для AI-поиска).
- JSON-LD: `TravelAgency` + `FAQPage` на главной, `TouristTrip` + `BreadcrumbList` + `FAQPage` (+ `AggregateOffer`
  при цене) на туре, `BlogPosting` + `BreadcrumbList` на статье, `ItemList` на списках. Нет `WebSite`, нет
  `Person` для автора с ссылкой на about, `sameAs` только Instagram, нет `hasMap`/`geo`.
- Картинки: alt везде, но у галерей «…tour in Kyrgyzstan, photo N» (есть куда расти), нет `width/height`.
- `hreflang` отсутствует (пока верно). Шаблоны к нему не готовы: `lang` и `<head>` собираются в `pages.js`,
  туда и добавится.

### 3.2 Поисковый интент и названия
Текущие title: «Song-Kul Horse Trek - 3 Days | Azat Tours» (сервер добавляет «, Kyrgyzstan», если влезает).
Запросы, которые реально вводят: «kyrgyzstan horse trek», «song kul horse trek 3 days», «kyrgyzstan tour 10 days»,
«kyrgyzstan road trip itinerary», «ala kul trek guided», «bishkek day trips». У 60 из 77 туров название начинается
с топонима, которого иностранец ещё не знает. Формула для фазы 3: `[запрос] + [уникальная деталь]`, slug не трогаем.

### 3.3 Каннибализация (19 серий)
| Серия (поле `series`) | Длительности | Проблема |
|---|---|---|
| kyrgyzstan-ultimate-road-trip | 7, 8, 9, 10, 11, 12 | шесть страниц под «Kyrgyzstan road trip» |
| best-of-kyrgyzstan | 8, 9, 10, 11, 12 | пять под «Kyrgyzstan tour 10 days», две уже с canonical |
| kyrgyzstan-horseback-riding-tour | 5, 6, 7, 10 | четыре под «Kyrgyzstan horse riding tour» |
| song-kol-lake-on-horseback | 2, 3, 4 (+ 5 новых Song-Kul туров пачки 2 без `series`) | до восьми под «Song-Kul horse trek» |
| ещё 15 серий по 1–2 тура | | |
Сейчас серии связаны строкой «Also available as: 2 days · 4 days». Этого мало: нужна одна сильная страница
на запрос (хаб или «главный» тур) и варианты как её части. Решение в фазе 3 с таблицей по каждой группе.

### 3.4 Внутренние ссылки (граф по локальной сборке)
- Главная → 6 туров (featured) + 5 категорий каталога + 4 карточки must-see → `/tours/`.
- Каталог → все 77 туров (плоско, одной страницей). Глубина любого тура = 2 клика, это хорошо.
- Тур → 3 «похожих» тура (по категории) + варианты серии. **Тур → статья: 0 ссылок.**
- Статья → 2–3 тура (есть у всех 9), статья → статья есть. Две статьи (`real-local-guides`, `easy-from-abroad`)
  никто не цитирует кроме `/blog/`.
- 37 туров получают ссылки только из каталога; 19 туров упомянуты в блоге.
- В данных статей ссылки записаны старым форматом `tour.html?slug=`, переписываются при рендере. Работает,
  но лучше привести данные к `/tours/<slug>/` миграцией.
План: карта «тур → релевантные статьи» (по тегам: ala-kul → гайд, yurt → этикет, winter → сезон, все →
visas/easy-from-abroad), блок «Read before you go» на туре; хабы направлений дадут каждому туру 1–2 входящих.

### 3.5 Контент и E-E-A-T
- Туры: в среднем 1670 слов, маршруты по дням, FAQ из полей. Сильная сторона. Но «What to pack» и «Before you go»
  одинаковы на 79 страницах (шаблонный текст, Google его обесценивает), summary и хайлайты повторяются 2–3 раза.
- Блог: 9 статей, 800 слов в среднем, последняя от 2 июня. Нет гайдов по Song-Kul, Kel-Suu, Issyk-Kul, сборам,
  визе отдельно, стоимости поездки, «7/10 days itinerary». Это и есть будущие хабы.
- Автор: «Azat, founder & guide», about-страница от первого лица. В `BlogPosting` автор пока `Organization`.
- Отзывы: ноль. Нет ссылок на внешние профили. Цены: 32 тура «from $», 47 «on request».
- Главная: H1 «Trek the Tian Shan. Sleep in yurts. Ride with nomads» без слова Kyrgyzstan.

### 3.6 Доступность (из Lighthouse)
- Нет `<main>` на главной и каталоге (`landmark-one-main`); на туре есть.
- Каталог: пропуск уровня заголовка (`<h4>` после `<h2>`).
- Тур: контраст кнопки WhatsApp в форме (`.form-wa`), `role="tablist"` без `role="tab"` у кнопок.

## 4. План правок по приоритету

Пакеты независимы, каждый проверяется краулером (`compare.js` против baseline) и Lighthouse до/после.

### Пакет A. Скорость без изменения дизайна (1–2 дня, самый высокий эффект)
1. Hero виден сразу; `.reveal` ниже первого экрана как раньше.
2. gtag после `load`/idle; `chat.js` по idle.
3. `width`/`height` у всех `<img>` из метаданных (генератор в `cards.js`/`tour-page.js` + кэш размеров).
4. `srcset` 480/800/1280 для карточек, hero тура, галереи, must-see (сборка превью через `build-image-formats.js`).
5. Панель фильтров каталога без сдвига (резерв высоты или серверный рендер).
6. Версионированные CSS/JS (`/styles.css?v=<hash>` минимум, лучше имя файла) + `max-age=1y, immutable`.
7. Шрифты: самохостинг + subset. Варианты для владельца: (а) оставить три семейства, но локально и subset
   (минус ~40 КБ и один домен); (б) два семейства; (в) заголовочный + системный текст. Нужен его выбор.
Ожидание: Perf 85–95 mobile, LCP ≤ 2,8 с.

### Пакет B. Сервер (нужен доступ к VPS, 1–2 часа владельца или друга; я готовлю команды)
1. nginx: `http2 on;`, `gzip_static`/brotli, `expires` для `/img/`.
2. Ночной бэкап `content/` + `public/images/` + `partners/data/` за пределы VPS.
3. UptimeRobot на `/`.
4. Позже: Cloudflare (DNS + прокси), заодно HTTP/3 и защита от ботов. Совместимо с текущим Node.

### Пакет C. SEO-правки из фазы 1 брифа (2–3 дня)
1. Sights: пересчёт `places[]` из маршрута миграцией, проверка «место упомянуто в тексте» в `check-site.js`,
   таблица спорных случаев владельцу.
2. Дубли на странице тура: один экземпляр каждого блока в HTML, вкладки и десктоп из одной разметки.
3. «What to pack»/«Before you go»: 3–5 пунктов по типу тура + ссылка на гайд.
4. Sitemap: убрать `changefreq/priority`, `lastmod` служебных страниц из git-даты.
5. JSON-LD: `WebSite`, автор `Person` «Azat» → about, `sameAs` (ссылки от владельца), тест валидности.
6. Перелинковка: must-see → лучшие туры (пока нет хабов), тур → статьи, статьи → канонические ссылки в данных,
   `<main>` и уровни заголовков.
7. alt галерей с местом/сценой, где известно.

### Пакет D. Доверие и конверсия (фаза 2 брифа, данные от владельца)
Отзывы (`data/reviews.json`, рендер сервером, бейджи платформ), `priceFrom` + CSV цен, email в конфиге.

### Пакет E. Архитектура контента (фаза 3, только предложения)
Хабы направлений, таблица консолидации серий, новые title/H1 под запросы.

### Дальше
Astro (фаза 4) и корейская версия (фаза 5) по брифу. Пакеты A–C делаются на текущем стеке и переносятся в Astro
без потерь, потому что это данные и разметка, а не код фреймворка.
