# Azat Tours: архитектура (актуально на 2026-10-25)

Один Node-процесс отдаёт сайт, API заявок и чата и держит Telegram-бота владельца. Страницы рендерятся на сервере
из JSON-файлов контента в момент запроса и кэшируются в памяти. Правка в боте видна на сайте через секунду, без
сборки и деплоя. Код меняется через git: push в `main` проходит тесты и выкатывается автоматически.

```
Браузер ──HTTPS──▶ nginx (TLS) ──▶ Node: start.js
                                    ├─ server.js        маршруты, 301, статика, AVIF/WebP, ?w= копии, кэш-заголовки, API
                                    │   └─ lib/pages.js рендер HTML из content/*.json + шаблонов public/*.html
                                    └─ bot.js           админка владельца в Telegram (grammY), ежедневный бэкап
Данные:  content/*.json (на сервере, не в git)  ──regenerate──▶  public/*-data.js (для браузерных скриптов)
Деплой:  push в main ─▶ GitHub Actions: тесты ─▶ SSH: git reset, npm ci, migrate, regenerate, pm2 reload
```

## Как проходит запрос
1. `www.` и `http` → 301 на `https://azattours.com`.
2. Старые адреса (`tour.html?slug=`, `post.html?slug=`, `tours.html`, slug до переименования) → 301 на текущий адрес одним хопом.
3. `/`, `/tours/`, `/tours/<slug>/`, `/blog/…`, `/*.html`, `/sitemap.xml`, `/llms.txt` → `lib/pages.js`: шаблон + данные →
   `finalize()` (hero виден сразу, `?v=` у CSS/JS, `width/height` у картинок, email из `lib/contact.js`) → кэш в памяти по
   mtime файлов → gzip-кэш по ETag.
4. Статика: JPEG/PNG отдаются как AVIF/WebP по заголовку `Accept`; `?w=480|800|1280|1600` даёт уменьшенную копию из
   `.cache/img/`; `.bak`, `.tmp` и скрытые файлы не отдаются.
5. Кэш: HTML и данные `no-cache` (правки из бота видны сразу), CSS/JS с `?v=` и шрифты на год, картинки на неделю.

## Как меняется контент
- **Владелец** правит в боте: бот пишет `content/*.json` атомарно (`lib/fsx.js`), пересобирает `public/*-data.js`,
  ставит `updatedAt`. Сайт видит изменение в течение секунды.
- **Код** меняет существующий контент только миграцией: шаг в конце списка `MIGRATIONS` в `scripts/migrate.js`,
  входные данные в `scripts/migrations/`. Миграция выполняется один раз на сервере при деплое, перед ней сохраняется
  снимок `content/before-<id>/`, применённые записываются в `content/.migrations.json`. Старые миграции не менять.
- Новое поле данных: добавить в `blankTour()` / `blankReview()` в `lib/content.js`, бот сохраняет незнакомые поля как есть.

## Деплой, проверки, бэкап
- `push` в `main` → job `test` (тесты сайта и бота партнёров) → job `deploy` по SSH. Без зелёных тестов деплоя нет.
- После деплоя: `npm run check -- https://azattours.com` (все URL sitemap, canonical, H1, JSON-LD, ссылки, скорость-контракт).
- Бэкап: бот каждый день в 10:00 по Бишкеку присылает владельцу `content/` (по воскресеньям с фото); восстановление
  `npm run restore -- <файл>`.
- Порядок выкатки и отката: `seo-audit/deploy-checklist.md`.

## Правила, которые нельзя нарушать
- Не запускать `bot.js` локально с боевым токеном (сломает polling на сервере).
- Не править `public/*-data.js` руками и не коммитить `content/`, `config.json`.
- Не перезаписывать серверный контент скриптами, кроме миграций.
- Push в `main` = прод, делает только владелец.
- Публичный репозиторий: никаких упоминаний старого сайта владельца (`docs/PRIVATE-NOTES.md`, не в git).

## Известные ограничения и следующий шаг
- nginx отдаёт только HTTP/1.1, сервер в Сингапуре: каждое новое соединение стоит ~1 с. Инструкция: `docs/SERVER.md`.
- Сайт и бот в одном процессе: сбой бота перезапускает сайт. Разделение возможно (общаются через файлы), но нужно
  проверить чат-релей, делать отдельной задачей.
- Переезд на Astro отложен (решение владельца 2026-10-25): статическая сборка сломала бы живые правки из бота.
